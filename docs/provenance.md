# Asset provenance and the first-party export boundary

**Status: register and fail-closed validator only (BK-06 [#7](https://github.com/Jevelopers-neatHack-2026/brand-kit/issues/7)).** This records what the repository itself shows about where each file came from. It records **no approval, no rights clearance and no legal conclusion**, selects no licence, and does not make any release eligible. Source revision inspected: `91157ac` (main after BK-01).

Files: [`provenance/register.json`](../provenance/register.json) (per-file record), [`provenance/allowlist.json`](../provenance/allowlist.json) (production export allowlist, currently **empty**), [`tools/check_provenance.py`](../tools/check_provenance.py), [`tools/tests/test_provenance.py`](../tools/tests/test_provenance.py).

## Commands

Standard library only, Python 3.9+; offline; nothing installed, published, merged or sent; no consumer repository touched.

| Command | Meaning | Exit |
|---|---|---|
| `make check-provenance-register` | **Structural** validation. Every tracked file under `logo/ fonts/ references/ tokens/ docs/assets/` has exactly one record; each recorded sha256 and size equals the file's actual bytes; paths are safe (no absolute, `..`, backslash, symlink); every required field is present (`UNKNOWN` is a valid, honest value); classification rules hold (references, internal, third-party and licensed items are never release candidates; runtime font files stay source-only; first-party is never inferred for `references/`); notice files resolve; evidence references are a tracked path, a public `https` URL or an opaque `restricted:<id>`; no secret-like string or email address appears. Part of `make check`. | 0 when the structure is sound, even though almost everything is UNKNOWN |
| `make check-provenance` | **Production export eligibility.** Fails closed. Not part of `make check`. | **Nonzero today, by design** |
| `python3 tools/check_provenance.py --report` | Include/exclude decision per file. | 0 |
| `python3 tools/check_provenance.py --print-hashes` | Current sha256 of in-scope files, as an aid when refreshing the register by hand. | 0 |

`check-provenance` passes only when all hold: the structural checks pass; the allowlist is **reviewed** (status `reviewed`, reviewer, evidence, date all present) and **non-empty**; every allowlist entry names an exact path and sha256 that match both the register and the file bytes; each entry's register record is first-party (`first-party-canonical|generated|derived|readme`), is a `candidate`, has `approval.status: approved` with evidence, date and reviewer, `rights_status: cleared`, known `intended_uses`, `permitted_uses` and `restrictions`, and the entry's `use` is one of its permitted uses; a record whose notice is required lists that notice in the allowlist too, and a notice requirement of `UNKNOWN` blocks; no font file is ever listed; synthetic data is refused. **Independently of the allowlist, every record marked `core` must have `rights_status: cleared` and an approval**, so an otherwise complete register cannot release while core rights are unknown. Today the allowlist is empty and 19 core files have unknown rights, so the command exits 1. That is the expected result and not a failure of the tooling.

## Boundaries (BK-06.4)

- **event-intelligence owns** discovered customer, event, organizer and venue assets, candidate collection and rights/permission evaluation ([OWNERSHIP](architecture/OWNERSHIP.md)). This repository stores none of those. A discovered third-party candidate is never added to `logo/ fonts/ references/ tokens/`; it stays a reference by identifier in its owner's system.
- **Creative and production owners** enforce what enters a production bundle. This validator checks only this repository's first-party allowlist; it does not enforce another repository's bundle.
- **Brand-kit owns** its approved product identity and may document a boundary or a stable contract reference, not hold other parties' assets.

## Safe evidence references (BK-06.5)

Evidence and approval fields hold references only, in one of three forms: a tracked repository path (optionally `#anchor`), a plain public `https://` URL (no credentials, no query string), or `restricted:<opaque-id>` meaning the evidence is held by a named maintainer outside this public repository. Never put contracts, customer or account details, personal email addresses or credentials here. The validator rejects secret-like strings and email addresses and does not echo them.

Review of this change for secrets and personal data, 2026-10-12, limited scope: `gitleaks 8.30.1` (locally installed; nothing installed or called out) over git history (19 commits) and over the working tree reported **no leaks**. The register and allowlist were also scanned by the validator's own patterns. Not covered: the scanner finds known secret shapes only, not private contracts or customer details in prose; GitHub issue and PR text and bundled binaries were not scanned (image and font bytes were not inspected). Commit metadata carries two author email addresses, which are public git metadata and are not copied into any file here. This is not a claim that the repository is free of sensitive data.

## Updating the register

Hash drift is expected when other changes touch these files (the BK-03A token work will change `tokens/`). `make check-provenance-register` then fails with the actual hash. Refresh by hand with `--print-hashes`, update `sha256`, `size_bytes` and `source_revision`, and record why. A changed file invalidates any earlier approval for the old hash. A new file under the scope fails coverage until it gets a record. Replace `UNKNOWN` only with a reference to real evidence; never write an approval on someone's behalf. To make something exportable: resolve rights, record approval evidence and reviewer in the register, then add the exact path and hash to the allowlist in a reviewed change, per the [governance](brand-governance.md) decision process.
